TP2 Test Javadoc Template

Shared by Aditya Gupta (agupt515) so every member's tests look the same and Task 7.3 is met. Every test method gets its own Javadoc with three labeled parts: the requirement tested, how it is checked, and how to read the output. The Contributor requirements testbed (testingAutomation.ContributorRequirementsTestbed) follows this template exactly; see the requirements and tests list.

Template

/*****
 * <p> Test CR-NN Tn (positive | negative) </p>
 *
 * <p> <b>Requirement tested:</b> CR-NN, <the requirement in one sentence>. </p>
 *
 * <p> <b>How it is checked:</b> <the setup, the exact method(s) called, with which
 * inputs, and what is read back to confirm the result>. </p>
 *
 * <p> <b>How to read the output:</b> <the expected value of each printed check, and what
 * PASS or FAIL means for this requirement>. </p>
 */
@RequirementTest(requirement = ContributorRequirement.CRNN, number = n,
        kind = RequirementTest.Kind.POSITIVE, title = "<short title printed in the output>")
private static void crNNWhatIsShown() throws Exception {
    // arrange: create only the accounts and lessons this test needs
    // act: call the real method under test
    check("<what is checked>", expected, observed, <condition>);
}

Rules

ItemRule
Requirement IDUse the ID from ContributorRequirement (CR-01 to CR-18). Ask the testing owner to add a requirement before writing tests for something not listed.
Positive and negativeEvery requirement needs two or more tests: at least one positive (valid use succeeds) and one negative (invalid use is refused, or handled safely, and nothing changes). The testbed refuses to report "complete" otherwise.
Method namecrNN + what is shown, in camel case, such as cr04LockedFieldCannotChange.
OutputEach check prints expected: and observed: lines followed by ok or FAILED; a test prints PASS only if every check is ok. Never print PASS without comparing a stored or returned value.
DataUse the testbed's temporary database and fixture accounts, never the application's data/Team53 database.
Requirement comments in codeCode being tested names the requirement it satisfies in a comment (Tasks 3.5 and 4.5), so a reader can go from a test to the code.
Screenshot name (7.4)<requirement>_7.4_T<n>_<method>.png, such as CR-04_7.4_T2_cr04LockedFieldCannotChange.png, in source-screenshots/. They are generated by python3 document.py, not taken by hand.

Worked example

/*****
 * <p> Test CR-04 T2 (negative) </p>
 *
 * <p> <b>Requirement tested:</b> CR-04, a locked field cannot be changed by the Contributor.
 * </p>
 *
 * <p> <b>How it is checked:</b> the Curator locks the Category; Alice submits an update that
 * changes the Category from Testing to Design and the lesson is read back. </p>
 *
 * <p> <b>How to read the output:</b> expect LOCKED and the stored Category still Testing. </p>
 */

Printed output for that test:

CR-04 T2 [NEGATIVE] A locked Category cannot be changed
    update that changes the locked Category
        expected: LOCKED
        observed: LOCKED   ok
    stored category
        expected: Testing
        observed: Testing   ok
    PASS
